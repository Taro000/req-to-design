# req-to-design

[English](README.md) | 日本語

システムの要求から設計を作るエージェントスキルです。まずアーキテクチャを形づくるべき要求（設計を動かす要求）を決め、次にアーキテクチャ、上位設計、詳細設計の順に詳しくしていきます。設計の各段の後にはレビューを挟みます。出発点は [cuj-to-slo](https://github.com/Taro000/cuj-to-slo) の成果物（利用者、CUJ、機能要件、品質要求、非機能要件、SLO）です。そのため、どの設計の決定からでも、それが応える要求と利用者までたどれます。

> **状態: 実験的（0.1.0）。** まだ最初から最後まで通して実行していません。最初の結果は念入りに確認してください。

## 段とスキル

| 段 | スキル | 入力 | 出力 |
|---|---|---|---|
| 1 | `requirements-to-architecture-drivers` | 品質チェーンの成果物（`docs/quality/`）、利用者を経由しない設計の入力（技術制約、費用・納期・体制、チームの構成、将来の変更）、既存のコード | 設計を動かす要求: 品質と変更のシナリオ、制約、全体の原則、順位 |
| 2 | `architecture-drivers-to-architecture` | 段 1 の出力 | 案と根拠を備えた設計の決定、要素、5 つのビュー、脅威のモデル |
| 3 | `architecture-to-high-level-design` | 段 2 の出力 | OpenAPI と AsyncAPI の記述を添えたインタフェース、遅延の予算を付けた端から端の流れ、データの実体、共通の約束事 |
| 4 | `high-level-design-to-detailed-design` | 段 3 の出力（1 回の実行で 1 コンポーネント） | 事前条件と事後条件を備えたモジュール、状態、判断表、物理データ、確かめ方 |
| レビュー | `design-review` | 段 2、3、4 のどれかの出力 | 決めるべき段に宛てた指摘 |

レビューは、設計を書いたのとは別のセッションで動かしてください。指摘は、その項目を書いた段に戻ります。その段を再実行すると、受け入れるか退けるかが決まります。これらのスキルは `docs/quality/` には書き込みません。設計の途中で要求を変えるべきだと分かったときは報告書に書くので、品質チェーンを再実行するかどうかはあなたが決めてください。

## インストール

```sh
# 5 つのスキルすべてを、今のプロジェクトに入れる
npx skills add Taro000/req-to-design

# インストールせずに、スキルの一覧だけを見る
npx skills add Taro000/req-to-design --list

# 1 つのスキルを、Claude Code 用に、すべてのプロジェクトで使えるように入れる
npx skills add Taro000/req-to-design --skill design-review -a claude-code -g
```

品質チェーン（`npx skills add Taro000/cuj-to-slo`）の後に使うと、最もよく働きます。品質チェーンを使わない場合は、同じ情報を自分で渡してください。利用者と CUJ、受け入れ基準付きの機能要件、優先順位を付けた品質要求、測れる目標です。

## 使い方

それぞれ新しい依頼として実行します。

1. 「docs/quality/ から設計を動かす要求を導いて。技術制約: … 予算と納期: … チーム: … ロードマップ: …」
2. 「設計を動かす要求からアーキテクチャを設計して」
3. 新しいセッションで「アーキテクチャをレビューして」。指摘があれば「指摘を解決するために、アーキテクチャの段を再実行して」
4. 「上位設計を書いて」。新しいセッションでレビューし、指摘を同じように解決します。
5. 「ELM-02 の詳細設計を書いて」。`docs/design/4-detailed-design.md` にあるすべてのコンポーネントについて繰り返し、それぞれをレビューします。

どの段も、まず全体を下書きし、その後で不確かだった点をすべて質問します。すべての判断に「入力」「推定」「確認済み」の印が付くので、何があなたの入力から来て、何をエージェントが決めたのかが分かります。

どの段も長い作業です。詳細設計はコンポーネントごとに実行するので、中規模のシステムでは要求よりも多くの文書ができます。読み通す時間と、順位、設計の決定、設計上の値について合意する時間を見込んでください。

質問と成果物の言語は、あなたの言語とプロジェクトの文書の言語に合わせます。スキル自体は英語で書かれています。

## 成果物

```
docs/design/
├── 1-architecture-drivers.md … 3-high-level-design.md   段ごとの報告書
├── 4-detailed-design.md, 4-detailed-design/              索引と、コンポーネントごとの報告書
├── reviews/                                              レビューごとの報告書
├── design-context.yaml                                   設計の入力、利害関係者、今の構造
├── drv/  dec/  elm/  ifc/  dat/  mod/  fnd/             項目ごとに 1 つの YAML ファイル
└── ifc/specs/                                            OpenAPI と AsyncAPI の記述
```

YAML のキーと ID は英語に固定しているので、どの段も他の段のファイルを読めます。ビュー、流れ、状態遷移図は、報告書の中に Mermaid で書きます。

## スキルがしないこと

- 品質チェーンに書き込むこと。設計の途中で要求を変えるべきだと分かったら、報告書に課題として書きます。どうするかはあなたが決めます。
- 事業の数値を作ること。目標、期限、量、予算は、あなたか品質チェーンから受け取ります。足りないものは名前の付いた未定の値のまま残します。タイムアウトなどの設計上の値は、何に基づくかを添えて、仮の値として提案します。
- コードを書くこと。詳細設計はコードを書く手前までで、特定のプログラミング言語に依存しない書き方をします。
- 事業の優先順位を代わりに決めること。設計を動かす要求の順位、受け入れるリスクや技術的負債、先送りした決定、設計上の値には「要合意」の印を付けます。
- 運用手順書、業務手順、教育の内容を書くこと。インフラの設計は範囲に含みますが、その運用は含みません。

## 保守

`references/conventions.md`、`references/artifacts.md`、`references/glossary.md` は、すべてのスキルで同じ内容です。`npx skills add --skill` は 1 つのスキルのディレクトリだけを入れるからです。`shared/` で編集してから、次を実行してください。

```sh
scripts/sync-shared.sh          # shared/ をすべてのスキルにコピーする
scripts/sync-shared.sh --check  # どれかのコピーが違えば失敗する
```
