# req-to-design

[English](README.md) | 日本語

システムの要求から設計を作るエージェントスキルです。まずアーキテクチャを形づくるべき要求（設計を動かす要求）を決め、次にアーキテクチャ、上位設計、詳細設計の順に詳しくしていきます。設計の各段の後にはレビューを挟みます。出発点は [cuj-to-slo](https://github.com/Taro000/cuj-to-slo) の成果物（利用者、CUJ、機能要件、品質要求、非機能要件、SLO）です。そのため、どの設計の決定からでも、それが応える要求と利用者までたどれます。

> **状態: 実験的（0.2.0）。** 実際のデモのプロジェクトで一度使いました。0.2.0 では、質問の仕方、仮定の記録、履歴の持ち方を変え、要求の側が決めなくなった設計の判断（プラットフォーム、仕組み、SLI のイベントの出どころ）を引き受けました。この版はまだ通しで実行していないので、最初の結果は念入りに確認してください。

## 段とスキル

| 段 | スキル | 入力 | 出力 |
|---|---|---|---|
| 1 | `requirements-to-architecture-drivers` | 品質チェーンの成果物（`docs/quality/`。品質チェーンが入力の中で見つけた設計の判断を含む）、利用者を経由しない設計の入力（技術制約、費用・納期・体制、チームの構成、将来の変更）、既存のコード | 設計を動かす要求: 品質と変更のシナリオ、制約、全体の原則、順位 |
| 2 | `architecture-drivers-to-architecture` | 段 1 の出力 | 案と根拠を備えた設計の決定、要素、5 つのビュー、脅威のモデル |
| 3 | `architecture-to-high-level-design` | 段 2 の出力 | インタフェース（端末、ほかのチーム、外部のシステムが使うものには OpenAPI と AsyncAPI の記述）、遅延の予算を付けた端から端の流れ、データの実体、共通の約束事、各 SLI のイベントの出どころ |
| 4 | `high-level-design-to-detailed-design` | 段 3 の出力（1 回の実行で 1 コンポーネント） | 契約と確かめ方を備えたモジュール。状態、判断表、データの制約は、コードで間違えると高くつくモジュールだけ。実装への申し送り |
| レビュー | `design-review` | 段 2、3、4 のどれかの出力 | 決めるべき段に宛てた指摘 |

レビューは、設計を書いたのとは別のセッションで動かしてください。指摘は、その項目を書いた段に戻ります。重大か中の指摘があれば、その段を再実行して、受け入れるか退けるかを決めます。軽微な指摘は、その段が別の理由で動くときにまとめて処理します。レビューをやり直すのは、重大か中の指摘でその段の項目が変わったときだけで、そのレビューは前回から変わった所だけを見ます。これらのスキルは `docs/quality/` には書き込みません。設計の途中で要求を変えるべきだと分かったときは報告書に書くので、品質チェーンを再実行するかどうかはあなたが決めてください。

## インストール

```sh
# 5 つのスキルすべてを、今のプロジェクトに入れる
npx skills add Taro000/req-to-design

# インストールせずに、スキルの一覧だけを見る
npx skills add Taro000/req-to-design --list

# 1 つのスキルを、Claude Code 用に、すべてのプロジェクトで使えるように入れる
npx skills add Taro000/req-to-design --skill design-review -a claude-code -g
```

品質チェーン（`npx skills add Taro000/cuj-to-slo`）の後に使うと、最もよく働きます。品質チェーンを使わない場合は、同じ情報を自分で渡してください。利用者と CUJ、受け入れ基準付きの機能要件、優先順位を付けた品質要求、測れる目標です。

## 使い方

それぞれ新しい依頼として実行します。

1. 「docs/quality/ から設計を動かす要求を導いて。技術制約: … 予算と納期: … チーム: … ロードマップ: …」
2. 「設計を動かす要求からアーキテクチャを設計して」
3. 新しいセッションで「アーキテクチャをレビューして」。重大か中の指摘があれば「指摘を解決するために、アーキテクチャの段を再実行して」。それでアーキテクチャが変わったら、新しいセッションでもう一度レビューします。
4. 「上位設計を書いて」。新しいセッションでレビューし、指摘を同じように解決します。
5. 「ELM-02 の詳細設計を書いて」。`docs/design/4-detailed-design.md` にあるすべてのコンポーネントについて繰り返し、それぞれをレビューします。
6. `docs/design/4-detailed-design.md` から実装します。その「実装への申し送り」が、設計が決めたこと、コードが決めること、コードが設計の決定を守れないときの指摘の書き方を、コーディングエージェントに伝えます。

どの段も、まず全体を下書きします。その後で、不確かだった点を影響の広さ（どれだけの項目がそれに依存するか）と重大さ（下書きが間違っていたときの害）で評価し、どちらかが「高」の点だけを質問します。設計を動かす要求の順位や、リスク、費用、負債を受け入れる決定も同じように評価し、質問したものはあなたの回答がそのまま決定になります。それ以外の点は下書きのまま進めて仮定として記録し、最後に一覧で示します。目を通して、違うものがあれば直せます。すべての判断に「入力」「推定」「仮定」「確認済み」の印が付くので、何があなたの入力から来て、何をエージェントが決め、何がまだ誰にも確かめられていないのかが分かります。

どの段も、細部まで決めるのは後で直しにくいことだけです。`conventions.md` がその段に挙げる種類の点と、影響の広さか重大さが「高」の点がそれに当たります。それ以外は、守る枠を添えて、それを決める後の段か実装へ申し送ります。どの段も、自分宛ての申し送りを引き取ります。

どの段も長い作業です。詳細設計はコンポーネントごとに実行します。詳しく書くのは、コードで間違えると高くつくモジュールだけで、ほかは実装に申し送ります。読み通す時間と、重要な質問に答える時間を見込んでください。

報告書と各項目には今の状態だけを書き、履歴は git に任せます。どのスキルも実行の最後に、自分が書いたファイルを変更の理由を書いたメッセージでコミットし、次の実行ではそこからの差分を読みます。

どのスキルも、コミットの前に `scripts/` の 2 つのスクリプトを動かします。`tables.py` は、報告書の索引の表を YAML の項目から作ります。手で写した表がずれることをなくすためです。`check.py` は、判断の要らないことを決まった手順で確かめます。レビューの指摘をそこに使わないためです。確かめるのは、どの YAML も読めて、値が引用符のない ` #` で切れていないこと、ID が実在する項目を指すこと、根拠の印が仮定と合うこと、機能と要求の割り当てが要素からインタフェースとモジュールまで食い違わないこと、OpenAPI と AsyncAPI の記述がインタフェースの操作、エラーの状態コード、エラーの符号を持つこと、などです。スキルは、自分のファイルについて報告された問題を直します。スクリプトは Python 3.8 以降だけで動き、パッケージは要りません。自分で検査を動かすときは、プロジェクトの根から `python3 <スキルのディレクトリ>/scripts/check.py` を実行します（Claude Code では、スキルのディレクトリは `.claude/skills/<スキル>/`）。

質問と成果物の言語は、あなたの言語とプロジェクトの文書の言語に合わせます。スキル自体は英語で書かれています。

## 成果物

```
docs/design/
├── 1-architecture-drivers.md … 3-high-level-design.md   段ごとの報告書
├── 4-detailed-design.md, 4-detailed-design/              実装への申し送りを含む索引と、コンポーネントごとの報告書
├── reviews/                                              段ごとの最新のレビューの報告書
├── design-context.yaml                                   設計の入力、利害関係者、今の構造
├── drv/  dec/  elm/  ifc/  dat/  mod/  fnd/             項目ごとに 1 つの YAML ファイル
├── hnd/                                                  申し送りごとに 1 つの YAML ファイル（段が後の段か実装に決めさせる点）
├── das/                                                  質問せずに置いた仮定ごとに 1 つの YAML ファイル
└── ifc/specs/                                            OpenAPI と AsyncAPI の記述
```

YAML のキーと ID は英語に固定しているので、どの段も他の段のファイルを読めます。ビュー、流れ、状態遷移図は、報告書の中に Mermaid で書きます。報告書の索引の表（`<!-- generated: ... -->` の印の間）は YAML の項目から作るので、直すときは表ではなく項目を直してください。

## スキルがしないこと

- 品質チェーンに書き込むこと。設計の途中で要求を変えるべきだと分かったら、報告書に課題として書きます。どうするかはあなたが決めます。
- 事業の数値を作ること。目標、期限、量、予算は、あなたか品質チェーンから受け取ります。足りないものは名前の付いた未定の値のまま残します。タイムアウトなどの設計上の値は、何に基づくかを添えて、仮の値として提案します。
- コードを書くこと。詳細設計はコードを書く手前までで、特定のプログラミング言語に依存しない書き方をします。
- 事業の優先順位を代わりに決めること。設計を動かす要求の順位、受け入れるリスクや技術的負債、段が細部まで決めるべきことの先送り、設計上の値は事業の判断です。影響の広さか重大さが「高」のものは質問し、それ以外は暫定的に採用して仮定として記録します。決まったものとして示すことはありません。
- 運用手順書、業務手順、教育の内容を書くこと。インフラの設計は範囲に含みますが、その運用は含みません。

## 保守

`references/conventions.md`、`references/artifacts.md`、`references/glossary.md` と `scripts/` のスクリプトは、すべてのスキルで同じ内容です。`npx skills add --skill` は 1 つのスキルのディレクトリだけを入れるからです。`shared/` と `shared/scripts/` で編集してから、次を実行してください。

```sh
scripts/sync-shared.sh          # shared/ をすべてのスキルにコピーする
scripts/sync-shared.sh --check  # どれかのコピーが違えば失敗する
python3 -m unittest discover -s tests   # スクリプトと、スキルの中の YAML の例が読めることを確かめる
```
