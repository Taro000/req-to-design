# req-to-design

[English](README.md) | 日本語

システムの要求から設計を作るエージェントスキルです。まずアーキテクチャを形づくるべき要求（設計を動かす要求）を決め、次にアーキテクチャ、技術方針、上位設計、詳細設計の順に詳しくしていきます。設計の各段の後にはレビューを挟みます。出発点は [cuj-to-slo](https://github.com/Taro000/cuj-to-slo) の成果物（利用者、CUJ、機能要件、品質要求、非機能要件、SLO）です。そのため、どの設計の決定からでも、それが応える要求と利用者までたどれます。

## 段とスキル

| 段 | スキル | 入力 | 出力 |
|---|---|---|---|
| 1 | `requirements-to-architecture-drivers` | 品質チェーンの成果物（`docs/quality/`。品質チェーンが入力の中で見つけた設計の判断を含む）、利用者を経由しない設計の入力（組織のエンジニアリングの標準を含む技術制約、費用・納期・体制、チームの構成、将来の変更）、既存のコード | 設計を動かす要求: 品質と変更のシナリオ、制約、全体の原則、順位 |
| 2 | `architecture-drivers-to-architecture` | 段 1 の出力 | 案と根拠を備えた設計の決定、ランタイムとプラットフォームを決めた要素、4 つのビュー（外部との関係、実行時の構成、配置、情報）、脅威のモデル |
| 2b | `architecture-to-technical-policy` | 段 2 の出力、品質チェーンのゲートと監査、組織のエンジニアリングの標準と既存のコードの約束事 | 後の段とコードが従う技術方針: コンポーネントの種類ごとの技術の組み合わせ、リポジトリとディレクトリと CI で確かめる依存の規則、品質チェーンの各ゲートをどこで何によって確かめるかと各監査の置き場所を含むテスト戦略、パイプラインとコードの中の約束事、インタフェースの種類ごとに仕様書を手で書くかコードから生成するか、コーディングエージェントが設計を見つけて指摘を戻す方法 |
| 3 | `architecture-to-high-level-design` | 段 2 と 2b の出力 | インタフェース（技術方針が仕様書を手で書くと決めたものには OpenAPI と AsyncAPI の記述）、遅延の予算を付けた端から端の流れ、データの実体、インタフェースの共通の約束事、各 SLI のイベントの出どころ |
| 4 | `high-level-design-to-detailed-design` | 段 3 の出力と技術方針（1 回の実行で 1 コンポーネント） | 契約を備え、技術方針のディレクトリに置き、そのテストの層で確かめるモジュール。状態、判断表、データの制約は、コードで間違えると高くつくモジュールだけ。実装への申し送り |
| レビュー | `design-review` | 段 2、2b、3、4 のどれかの出力 | 決めるべき段に宛てた指摘 |

Claude Code では、7 つ目のスキル `design-chain` が、段とレビューを代わりに動かします（下の「design-chain で連鎖を動かす」）。

レビューは、設計を書いたのとは別のセッションで動かしてください。指摘は、その項目を書いた段に戻ります。重大か中の指摘があれば、その段を再実行して、受け入れるか退けるかを決めます。軽微な指摘は、その段が別の理由で動くときにまとめて処理します。レビューをやり直すのは、重大か中の指摘でその段の項目が変わったときだけで、そのレビューは前回から変わった所だけを見ます。これらのスキルは `docs/quality/` に書き込まず、品質チェーンが決めること（目標や、リリース前の確かめなど）も決めません。品質チェーンの要求を変えるべきだと設計で分かったときや、設計に要る要求が品質チェーンにないときは、段が品質チェーンへの要求を書きます。品質チェーンへの要求は `docs/design/quality-chain-requests.md`（要求書）に集まるので、答えて品質チェーンに渡してください。

## インストール

```sh
# 7 つのスキルすべてを、今のプロジェクトに入れる
npx skills add Taro000/req-to-design

# インストールせずに、スキルの一覧だけを見る
npx skills add Taro000/req-to-design --list

# 1 つのスキルを、Claude Code 用に、すべてのプロジェクトで使えるように入れる
npx skills add Taro000/req-to-design --skill design-review -a claude-code -g
```

品質チェーン（`npx skills add Taro000/cuj-to-slo`）の後に使うと、最もよく働きます。品質チェーンを使わない場合は、同じ情報を自分で渡してください。利用者と CUJ、受け入れ基準付きの機能要件、優先順位を付けた品質要求、測れる目標です。

## 使い方

それぞれ新しい依頼として実行します。

1. 「docs/quality/ から設計を動かす要求を導いて。技術制約: … エンジニアリングの標準: … 予算と納期: … チーム: … ロードマップ: …」
2. 「設計を動かす要求からアーキテクチャを設計して」
3. 新しいセッションで「アーキテクチャをレビューして」。重大か中の指摘があれば「指摘を解決するために、アーキテクチャの段を再実行して」。それでアーキテクチャが変わったら、新しいセッションでもう一度レビューします。
4. 「技術方針を決めて」。新しいセッションでレビューし、指摘を同じように解決します。後の段とコードが従うことを、すべてのコンポーネントについて一度だけ決めます。コンポーネントの種類ごとの技術の組み合わせ、リポジトリと依存の規則、品質チェーンの各ゲートを確かめる所を含むテスト戦略、パイプラインとコードの中の約束事、インタフェースの種類ごとの仕様書の作り方です。ほかの段はこれらを決めません。アーキテクチャは各コンポーネントのランタイムとプラットフォームまでを決め、上位設計は方針が手で書くとしたインタフェースにだけ仕様書を書き、詳細設計は種類ごとの技術の組み合わせの上で各コンポーネントを設計します。
5. 「上位設計を書いて」。新しいセッションでレビューし、指摘を同じように解決します。
6. 「ELM-02 の詳細設計を書いて」。`docs/design/4-detailed-design.md` にあるすべてのコンポーネントについて繰り返し、それぞれをレビューします。
7. `docs/design/4-detailed-design.md` から、`docs/design/2b-technical-policy.md` の技術方針に従って実装します。「実装への申し送り」が、設計が決めたこと、コードが決めること、コードが設計の決定や方針を守れないときの指摘の書き方を、コーディングエージェントに伝えます。

品質チェーンへの要求は `docs/design/quality-chain-requests.md`（要求書）に集まります。段がその場で質問するのは、答えによって、主な設計を動かす要求か、後で直しにくい決定が変わる品質チェーンへの要求だけです。ほかの品質チェーンへの要求は答えを待ち、設計は品質チェーンの今の要求のまま進みます。答えが決まったら、いつでも要求書の「答え:」の後に書いてください。次の実行がそれを品質チェーンへの要求に写します。そのうえで要求書を、そこに挙げた品質チェーンの段に渡して再実行します。設計の段は、次の実行で変わった所に追随します。

どの段も、まず全体を下書きします。その後で、不確かだった点を影響の広さ（どれだけの項目がそれに依存するか）と重大さ（下書きが間違っていたときの害）で評価し、どちらかが「高」の点だけを質問します。設計を動かす要求の順位や、リスク、費用、負債を受け入れる決定も同じように評価し、質問したものはあなたの回答がそのまま決定になります。それ以外の点は下書きのまま進めて仮定として記録し、最後に一覧で示します。目を通して、違うものがあれば直せます。すべての判断に「入力」「推定」「仮定」「確認済み」の印が付くので、何があなたの入力から来て、何をエージェントが決め、何がまだ誰にも確かめられていないのかが分かります。

人が直接段を動かすときは、その場で質問します。ほかのエージェントのサブエージェントとして動くときや、誰も見ていない所で動くときのように質問できないときは、同じ選択肢を添えて質問を報告書の「未回答の質問」に書き、報告書の状態を「質問待ち」にして、下書きをコミットして止まります。各質問の行に答えを書いて段をもう一度動かすと、答えを反映して「決めたこと」に移します。それまでは、後の段もその段のレビューも動かしません。

段は、古くなったらもう一度動かします。前回の実行の後に、読む項目が変わった、重大か中の指摘が届いた、自分宛ての申し送りの契機が来た、項目が依存する仮定が覆った、のどれかが起きた段と、「未回答の質問」に答えが書かれた段です（`conventions.md` の「Re-running a stage」）。`scripts/status.py` が、古い段とその理由、次に動かすものを示します。

どの段も、細部まで決めるのは後で直しにくいことだけです。`conventions.md` がその段に挙げる種類の点と、影響の広さか重大さが「高」の点がそれに当たります。それ以外は、守る枠を添えて、それを決める後の段か実装へ申し送ります。どの段も、自分宛ての申し送りを引き取ります。

どの段も長い作業です。詳細設計はコンポーネントごとに実行します。詳しく書くのは、コードで間違えると高くつくモジュールだけで、ほかは実装に申し送ります。読み通す時間と、重要な質問に答える時間を見込んでください。

報告書と各項目には今の状態だけを書き、履歴は git に任せます。どのスキルも実行の最後に、自分が書いたファイルを変更の理由を書いたメッセージでコミットし、次の実行ではそこからの差分を読みます。

どのスキルも、コミットの前に `scripts/` の 2 つのスクリプトを動かします。`tables.py` は、報告書の索引の表と要求書を YAML の項目から作ります。手で写したものがずれることをなくすためです。`check.py` は、判断の要らないことを決まった手順で確かめます。レビューの指摘をそこに使わないためです。確かめるのは、どの YAML も読めて、値が引用符のない ` #` で切れていないこと、ID が実在する項目を指すこと、根拠の印が仮定と合うこと、機能と要求の割り当てが要素からインタフェースとモジュールまで食い違わないこと、OpenAPI と AsyncAPI の記述がインタフェースの操作、エラーの状態コード、エラーの符号を持つこと、品質チェーンのどのゲートと監査にも技術方針の中に置き場所があること、などです。スキルは、自分のファイルについて報告された問題を直します。3 つ目の `status.py` は、連鎖の状態を示します。どの段が古く、なぜか、どれが質問待ちか、どのレビューを動かすべきか、次に何を動かすかです。スクリプトは Python 3.8 以降だけで動き、パッケージは要りません。自分で検査を動かすときは、プロジェクトの根から `python3 <スキルのディレクトリ>/scripts/check.py` を実行します（Claude Code では、スキルのディレクトリは `.claude/skills/<スキル>/`）。

質問と成果物の言語は、あなたの言語とプロジェクトの文書の言語に合わせます。スキル自体は英語で書かれています。

### design-chain で連鎖を動かす

Claude Code では、`design-chain` が上の手順を代わりに進めます。古い段を見つけ、連鎖の上から順に一つずつ、その段のスキルをサブエージェントで動かします。レビューは、段の初回の後と、重大か中の指摘でその段が変わった後にだけ動かします。指摘、申し送り、品質チェーンが反映した要求は、それが求める実行をそのまま始めます。途中であなたに聞くのは、あなたにしか答えられない質問だけです。

- 始める: 「docs/quality/ から設計の連鎖を動かして。技術制約: … エンジニアリングの標準: … 予算と納期: … チーム: … ロードマップ: …」。渡した内容で第 1 段階を動かし、各コンポーネントの詳細設計まで進めます。
- 続ける: 「設計の連鎖を続けて」。報告書の質問に答えた後、仮定を直した後、要求書を品質チェーンに渡して再実行した後、実装が指摘を出した後、上限で止まった後に使います。
- 状態を見る: 「設計の連鎖の状態を見せて」。何も動かさず、古い段とその理由、質問待ちのもの、次に動かすもの、後で段を古くするものを示します。スクリプトを自分で動かすこともできます: `python3 .claude/skills/design-chain/scripts/status.py`。

実行中に誰も答えられない質問を段が書いたときは、その答えに依存しない段を先に動かし、溜まった質問を段ごとにまとめて聞きます。答えを報告書に書き、その段を再開させます。それまで、質問待ちの段より下の段は止めたままです。

同じ起動の中で項目が前の値に戻ったとき（振動）、上限に達したとき（既定は 1 回の起動で 10 回、同じ段は 3 回まで）、2 巡しても重大な指摘が残るときは、自分で止まって理由を示します。上限は、依頼（「上限 20 回で続けて」）か `docs/design/design-chain.yaml` で変えられます。終わりに、動いた段とそのコミット、聞いた質問とあなたの答え、未確認の仮定（直したいものは直せます）、未回答と回答済みの品質チェーンへの要求と、それぞれが古くする段を示します。各段は今どおり自分の実行をコミットします。`design-chain` 自身は何もコミットせず、push もしません。

段の入口で人が確かめないので、誤っていて「高」と評価されなかった仮定は、下の段へ流れます。各実行は自分が依存する未確認の仮定を評価し直し、依存する項目が増えて「高」になった時点で聞きます。終わりに示す未確認の仮定に目を通し、誤ったものは直してください。

ほかのエージェントでは、`design-chain` は何も動かさず、次に動かす段、新しいセッションでの依頼文、待っている質問を示します。

## 成果物

```
docs/design/
├── 1-architecture-drivers.md … 3-high-level-design.md   段ごとの報告書（2b-technical-policy.md を含む）
├── 4-detailed-design.md, 4-detailed-design/              実装への申し送りを含む索引と、コンポーネントごとの報告書
├── reviews/                                              段ごとの最新のレビューの報告書
├── design-context.yaml                                   設計の入力、利害関係者、今の構造
├── design-chain.yaml                                     任意: design-chain の上限
├── drv/  dec/  elm/  pol/  ifc/  dat/  mod/  fnd/       項目ごとに 1 つの YAML ファイル
├── hnd/                                                  申し送りごとに 1 つの YAML ファイル（段が後の段か実装に決めさせる点）
├── das/                                                  質問せずに置いた仮定ごとに 1 つの YAML ファイル
├── qcr/                                                  品質チェーンへの要求ごとに 1 つの YAML ファイル
├── quality-chain-requests.md                             品質チェーンへの要求書（要求を 1 つにまとめ、品質チェーンに渡す文書）
└── ifc/specs/                                            OpenAPI と AsyncAPI の記述（技術方針が仕様書を手で書くと決めたインタフェースの分）
```

YAML のキーと ID は英語に固定しているので、どの段も他の段のファイルを読めます。ビュー、流れ、状態遷移図は、報告書の中に Mermaid で書きます。報告書の索引の表（`<!-- generated: ... -->` の印の間）は YAML の項目から作るので、直すときは表ではなく項目を直してください。

## スキルがしないこと

- 品質チェーンに書き込むことと、品質チェーンが決めること（要求、目標、しきい値、マージやデモ、リリースの前に通すべきゲート）を決めること。品質チェーンの要求を変えるべきだと設計で分かったら、品質チェーンへの要求として 1 つの文書（要求書）にまとめます。答えるのも、品質チェーンに渡す時期を決めるのも、あなたです。
- 事業の数値を作ること。目標、期限、量、予算は、あなたか品質チェーンから受け取ります。足りないものは名前の付いた未定の値のまま残します。タイムアウトなどの設計上の値は、何に基づくかを添えて、仮の値として提案します。
- コードを書くこと。詳細設計はコードを書く手前までで、特定のプログラミング言語に依存しない書き方をします。
- 事業の優先順位を代わりに決めること。設計を動かす要求の順位、受け入れるリスクや技術的負債、段が細部まで決めるべきことの先送り、設計上の値は事業の判断です。影響の広さか重大さが「高」のものは質問し、それ以外は暫定的に採用して仮定として記録します。決まったものとして示すことはありません。
- 運用手順書、業務手順、教育の内容を書くこと。インフラの設計は範囲に含みますが、その運用は含みません。

## 保守

`references/conventions.md`、`references/artifacts.md`、`references/glossary.md` と `scripts/` のスクリプトは、すべてのスキルで同じ内容です。`npx skills add --skill` は 1 つのスキルのディレクトリだけを入れるからです。`shared/` と `shared/scripts/` で編集してから、次を実行してください。

```sh
scripts/sync-shared.sh          # shared/ をすべてのスキルにコピーする
scripts/sync-shared.sh --check  # どれかのコピーが違えば失敗する
python3 -m unittest discover -s tests   # スクリプトと、スキルの中の YAML の例が読めることを確かめる
```
